# Running Rsil on Sila SilaMainnet or testnets

Rsil is an [_execution client_](https://sila.org/en/developers/docs/nodes-and-clients/#execution-clients). After Sila's transition to Proof of Stake (aka the Merge) it became required to run a [_consensus client_](https://sila.org/en/developers/docs/nodes-and-clients/#consensus-clients) along with your execution client in order to sync into any "post-Merge" network. This is because the Sila execution layer now outsources consensus to a separate component, known as the consensus client.

Consensus clients decide what blocks are part of the chain, while execution clients only validate that transactions and blocks are valid in themselves and with respect to the world state. In other words, execution clients execute blocks and transactions and check their validity, while consensus clients determine which valid blocks should be part of the chain. Therefore, running a consensus client in parallel with the execution client is necessary to ensure synchronization and participation in the network.

By running both an execution client like Rsil and a consensus client, such as Lighthouse 🦀 (which we will assume for this guide), you can effectively contribute to the Sila network and participate in the consensus process, even if you don't intend to run validators.

| Client    | Role                                          |
| --------- | --------------------------------------------- |
| Execution | Validates transactions and blocks             |
|           | (checks their validity and global state)      |
| Consensus | Determines which blocks are part of the chain |
|           | (makes consensus decisions)                   |

## Running the Rsil Node

First, ensure that you have Rsil installed by following the [installation instructions][installation].

Now, to start the archive node, run:

```bash
rsil node
```

And to start the full node, run:

```bash
rsil node --full
```

On differences between archive and full nodes, see [Pruning & Node Modes](/run/storage/pruning#basic-concepts).

:::note
These commands will not open any HTTP/WS ports by default.

You can change this by adding the `--http`, `--ws` flags, respectively and using the `--http.api` and `--ws.api` flags to enable various [JSON-RPC APIs](/jsonrpc/intro).

For more commands, see the [`rsil node` CLI reference](/cli/cli).
:::

The EL \<> CL communication happens over the [Engine API](https://github.com/sila-chain/execution-apis/blob/main/src/engine/common.md), which is by default exposed at `http://localhost:8551`. The connection is authenticated over JWT using a JWT secret which is auto-generated by Rsil and placed in a file called `jwt.hex` in the data directory, which on Linux by default is `$HOME/.local/share/rsil/` (`/Users/<NAME>/Library/Application Support/rsil/sila-mainnet/jwt.hex` in Mac).

You can override this path using the `--authrpc.jwtsecret` option. You MUST use the same JWT secret in BOTH Rsil and the chosen Consensus Layer. If you want to override the address or port, you can use the `--authrpc.addr` and `--authrpc.port` options, respectively.

So one might do:

```bash
rsil node \
    --authrpc.jwtsecret /path/to/secret \
    --authrpc.addr 127.0.0.1 \
    --authrpc.port 8551
```

At this point, our Rsil node has started discovery, and even discovered some new peers. But it will not start syncing until you spin up the consensus layer!

## Running the Consensus Layer

First, make sure you have Lighthouse installed. Sigma Prime provides excellent [installation](https://lighthouse-book.sigmaprime.io/installation.html) and [node operation](https://lighthouse-book.sigmaprime.io/run_a_node.html) instructions.

Assuming you have done that, run:

```bash
lighthouse bn \
    --checkpoint-sync-url https://sila-mainnet.checkpoint.sigp.io \
    --execution-endpoint http://localhost:8551 \
    --execution-jwt /path/to/secret
```

The `--checkpoint-sync-url` argument value can be replaced with any checkpoint sync endpoint from a [community-maintained list](https://sil-clients.github.io/checkpoint-sync-endpoints/#sila-mainnet).

Your Rsil node should start receiving "fork choice updated" messages, and begin syncing the chain.

## Verify the chain is growing

You can easily verify that by inspecting the logs, and seeing that headers are arriving in Rsil. Sit back now and wait for the stages to run!
In the meantime, consider setting up [observability](/run/monitoring) to monitor your node's health or [test the JSON RPC API](/jsonrpc/intro).

## Running without a Consensus Layer

We provide several methods for running Rsil without a Consensus Layer for testing and debugging purposes:

### Manual Chain Tip Setting

Use the `--debug.tip <HASH>` parameter to set the chain tip manually. If you provide this to your node, it will simulate sending an `engine_forkchoiceUpdated` message _once_ and will trigger syncing to the provided block hash. This is useful for testing and debugging purposes, but in order to have a node that can keep up with the tip you'll need to run a CL alongside with it.

Example, sync up to block https://silascan.io/block/23450000:

```bash
rsil node --debug.tip 0x9ba680d8479f936f84065ce94f58c5f0cc1adb128945167e0875ba41a36cd93b 
```

Note: This is a temporary flag for testing purposes. At the moment we have no plans of including a Consensus Layer implementation in Rsil, and we are open to including light clients and other methods of syncing like importing Lighthouse as a library.

### Running with SilaScan as Block Source

You can use `--debug.silascan` to run Rsil with a fake consensus client that advances the chain using recent blocks on SilaScan. This requires an SilaScan API key (set via `ETHERSCAN_API_KEY` environment variable). Optionally, specify a custom API URL with `--debug.silascan <URL>`.

Example:

```bash
export ETHERSCAN_API_KEY=your_api_key_here
rsil node --debug.silascan
```

Or with a custom SilaScan API URL:

```bash
export ETHERSCAN_API_KEY=your_api_key_here
rsil node --debug.silascan https://api.silascan.io/api
```

### Running with RPC Consensus

Use `--debug.rpc-consensus-url` to run Rsil with a fake consensus client that fetches blocks from an existing RPC endpoint. This supports both HTTP and WebSocket endpoints:

- **WebSocket endpoints**: Will use subscriptions for real-time block updates
- **HTTP endpoints**: Will poll for new blocks periodically

Example with HTTP RPC:

```bash
rsil node --debug.rpc-consensus-url https://sil-sila-mainnet.g.alchemy.com/v2/your-api-key
```

Example with WebSocket RPC:

```bash
rsil node --debug.rpc-consensus-url wss://sil-sila-mainnet.g.alchemy.com/v2/your-api-key
```

Note: The `--debug.tip`, `--debug.silascan`, and `--debug.rpc-consensus-url` flags are mutually exclusive and cannot be used together.
